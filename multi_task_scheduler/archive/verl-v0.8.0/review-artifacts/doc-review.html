四02 / 04§6.4 对模拟器 — 实质性差异

差异 模拟器仓库存在两个 GroupScheduler 实现，文档未区分，导致多处声称只对骨架成立、对生产模拟器不成立。
根因：/Users/nyp/Documents/multi-rl-task-scheduler 下有两个实现—— 生产模拟器 group_scheduler/group_scheduler.py:64（@yr.instance，benchmark 实际使用）与 协议骨架 src/multi_rl_task_scheduler/group_scheduler.py:18（自述"对齐 spec 的最小骨架，非完整生产调度器"）。 04§6.4 与 02 的"模拟器"指向不清，是所有差异的源头。
  • 实质04 §6.4 "模拟器原有接口"

    声称模拟器原有接口为 register_task(config, scheduler) / scheduler.assign(...) / scheduler.reclaim(...)。该 callback 模式只对骨架 src/ 成立；生产模拟器 register_task(config) 无 scheduler 参数，assign/reclaim 走 TaskInfo.assign.invoke 的 yr callable，方法名是 concurrent_assign/concurrent_reclaim。

    src/.../interfaces.py:21 register_task(self, config, scheduler: InferScheduler) group_scheduler/group_scheduler.py:129 def register_task(self, config: TaskConfig) -> bool group_scheduler/group_scheduler.py:1589 concurrent_reclaim / :1597 concurrent_assign
  • 实质04 §6.4 + 02 §4.1 unregister_task

    两文档都把 unregister_task(task_id, session_id) 列为接口。生产模拟器完全无此方法（grep 无命中）；骨架仅有单参数 unregister_task(task_id)，无 session_id。

    group_scheduler/group_scheduler.py grep "unregister" → 0 命中 src/.../group_scheduler.py:75 def unregister_task(self, task_id) # 无 session_id
  • 实质02 全套目标协议

    02 的 heartbeat/probe、apply_schedule_command、report_step_idle_replicas/STEP_IDLE_REPLICAS、session_id、task_runner_handle/ActorHandle——在两个模拟器实现中均无任何匹配。模拟器状态是被动 report_state，空闲由 GS 内部按 idle_instances 计算，无 LB 单向事件通道。02 是目标设计，非现状。

    全仓 grep "heartbeat|probe_seq|apply_schedule_command|STEP_IDLE_REPLICAS|session_id|task_runner_handle" → 0 命中 group_scheduler.py:135 def report_state(self, state, need_schedule=True)
  • 实质02 §1 映射表 类名

    映射表把 InferScheduler / RlxfScheduler 当作模拟器实际组件。RlxfScheduler 全仓不存在；InferScheduler 仅是骨架抽象基类，生产侧由 GSAdapter 的 expand_callback/reclaim_callback 模拟任务执行。

    全仓 grep "RlxfScheduler" → 0 命中 src/.../interfaces.py:9 class InferScheduler(ABC) # 仅骨架 gs-simulator/core/gs_adapter.py:1056-1066 expand_callback / reclaim_callback
  • 命名02 §3.5 / 04 §10.3 decision_id

    文档用 decision_id，生产模拟器实际用 action_id（V2ActionRecord.action_id、_next_v2_action_id）。概念对应，命名不符。decision_id 全仓 0 命中。

    group_scheduler.py:46 action_id: str / :738 _next_v2_action_id
  • 语义04/02 lease

    文档所述 lease 是"跨任务 worker 借用租约"，而模拟器的 leases 是 reclaim 事务的内部 worker token（prepare_external_no_sleep_reclaim 等），二者概念不同；跨任务借用租约在模拟器中未实现。

  • 一致04 §6.4 / §10.1 算法与账本

    "模拟器的算法和账本语义可以复用"、workers_per_instance = tp × pp 的警告、base_instances > 1、state_version 单调递增——均与代码一致，警告成立（直接照搬 tp×pp 到 verl 会丢 dp 维度，正是 04 §10.1 警告的内容）。

五建议修正

  1. 区分两个模拟器实现。04 §6.4 与 02 凡称"模拟器"处，应明确指向 src/multi_rl_task_scheduler/（骨架，与 callback 接口一致）还是 group_scheduler/（生产）。建议在 02 §1 顶部加一句声明"映射对象对应骨架 src/，生产模拟器接口不同"，避免读者误以为生产代码已具备目标协议。
  2. 标注目标协议 vs 现状。02 的 heartbeat / command / step-idle / session fencing 全是目标设计；建议在 02 标题或 §1 注明"本文为目标协议，模拟器尚未实现"，与 09 §6.1 明确标注 TaskRunner 需新增 concurrency group 的写法保持一致。
  3. 04 §8.2 措辞。把"TaskRunner 使用 training=1/heartbeat=1/command=1 三个 concurrency groups"改为"改造后 TaskRunner 将划分三个 concurrency groups"，与 §6.1 末尾"建议的新模式"口径统一。
  4. 04 §1 算法名。补回 GRPO，与 00 单一事实来源一致："GRPO + on-policy + sync + HYBRID"。
  5. 命名对齐。02/04 若要复用生产模拟器账本，将 decision_id 统一为 action_id，或在文档显式声明"对应模拟器 action_id"。
  6. lease 概念澄清。04/02 所述跨任务 worker lease 在模拟器中不存在；若属新增设计，应注明"新增，非复用模拟器现有 leases"。
  7. 09 可选补强。§7.3 补一句 max_concurrent_samples = min(replica_count×16, max_required_samples) 的实际上限，使"需改为可更新"的论据更完整。
