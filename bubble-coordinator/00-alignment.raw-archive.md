## 0. 项目一句话定义

基于 verl 开发独立组件，同时纳管多个训推同步 RL 任务，识别任务中的空闲推理实例、纳管空闲推理卡并重新分配给繁忙任务，按负载对 RL 任务推理侧扩缩容，降低端到端训练耗时。

## 1. 硬原则（用户拍板，不可违反）

- [x] **P1：不改 verl 现有架构**。任何方案若需修改 verl 核心代码，须显式标红并退回重设计。
- [x] **P2：独立组件 / 子项目，插件式接入 verl**。以 verl 现有扩展点（config / hooks / 外部进程对 vLLM/Ray 资源的控制）为集成面。
- [x] **P3：先对齐背景与约束，再谈技术路线；讨论全程留痕**（本文档即留痕载体）。

- [2026-07-10] 用户陈述（G2，目标场景，逐字记录）：**期望的部署/调度模型——公共资源池**：
  - 先启动一个 Ray 集群，该集群**初始不存在任何 RL 任务，是个公共资源池，不属于任何 RL 任务**。
  - 多个 RL 任务**不定时加入**该集群；每个任务**自带资源**，把资源**注册进公共集群**，然后启动训练。
  - 任何一个 RL 任务都可**将自己的资源贡献给其他任务使用**；公共资源池的资源会**分配给其他任务使用**。
  - 含义（重塑协调器设计模型，修正此前理解）：
    - **不是"几个任务各占一块卡、彼此错峰互借"的静态分片模型**，而是**动态贡献-共享池模型**：任务进集群时把自己的卡捐进公共池，池子统一调度，任何任务可从池里借资源。
    - 协调器角色 = **公共资源池的管理者/调度器**：维护池子、接受任务注册与资源贡献、按需把池资源借给繁忙任务、任务退出/空闲时回收。
    - 任务与资源**解耦**：资源不再"属于"某个任务，而是"任务贡献给池、池再分配给任务"。借调不是"从 A 任务借到 B 任务"，而是"从池里取/还"。
    - "纳管空闲推理卡"语义被精确化：空闲卡回收到公共池，而非停留在原任务名下。
  - 与既有结论的对照：
    - 与 §2A"G1=分离（目标态）"一致：分离是让"推理卡可独立闲置/可回收"的前提，公共池模型进一步要求这些卡能被统一纳管流转。
    - 与 G1 续澄清"分离尚未跑通"叠加：**项目要先有分离推理（让卡能脱离训练独立存在），才能有公共池流转**。两层关系明确：分离是池化的物理前提。
  - 追问/盲点（待澄清）：
    - "自带资源注册进公共集群"——任务自带的资源是 GPU/节点，还是 Ray placement group bundle？注册动作是 Ray 层面（actor/bundle）还是更高层？决定纳管粒度。
    - 资源"贡献给池"后，原任务自己还要不要独占保留一部分（自留额度）？还是全捐、用时再申请？影响调度公平与饥饿。
    - 公共池资源借给任务时，是借"整组推理实例"还是"裸卡"？裸卡需任务自己拉 vLLM（冷启动），整组实例可热接（但需权重一致）。
    - 任务"不定时加入"——有无退出/资源回收机制？任务崩溃后其贡献资源如何被池回收？
    - 公平/优先级：多任务竞争池资源时，调度策略（先来先服务？按贡献量？按负载/紧急度？）。
  - **[2026-07-10 用户回答池化落地 5 子问，逐条记录]：**
    - **P1-1（注册粒度/层级）**：任务自带的是**卡（GPU）**；协调器位于 **Ray 资源管理层之上，不替换 Ray**——Ray 负责资源分配，协调器只负责"资源给谁用"的归属/调度决策。即 Ray 做底层资源面，协调器做上层调度决策面，二者分层。
    - **P1-2（贡献策略）**：**只要有空闲卡就贡献，直到为 0**（全捐、不留自留额度）；需要时**待协调器分配**。= 激进全捐模型，池化效益最大化，但需协调器防饥饿（任务自己空泡时可能池里也被借空）。
    - **P1-3（借出形态）**：池借出的是**裸卡**；借入方需**重拉推理实例或预热**（即冷启动由借入方承担）。= 借调伴随 vLLM init+权重加载+warmup 冷启动成本，无热接。
    - **P1-4（退出回收）**：任务退出时其资源**需要回收**；可靠性等需考虑（崩溃/异常退出场景的资源释放与泄漏防护）。
    - **P1-5（调度策略）**：核心调度策略**现阶段暂不考虑**（先打通机制，调度算法后置）。
  - **三条回答间牵连出的硬矛盾（必须正视）：**
    - P1-2（全捐到 0）+ P1-3（借出裸卡/借入方冷启动）→ 借调收益高度依赖"空泡时长 ≫ 借调冷启动成本"。若某任务 training 段空泡仅几十秒，但借入裸卡要花分钟级拉 vLLM+加载权重+warmup，则借调净亏。这是 G6（冷启动成本基线）为何关键的原因。
    - P1-2（全捐）+ on-policy（G1 栈约束）→ 全捐意味着任务自己 generation 时也可能拿不回足够卡，需协调器保证 on-policy 一致性前提下，还能让任务在需要时借回。防饥饿与一致性双重压力。
    - P1-3（裸卡/重拉实例）+ on-policy → 重拉实例必须加载该任务**当前 step 权重**，否则 off-policy。冷启动成本里权重加载是刚性项，无法靠实例预热绕过（除非池里维护"该任务最新权重"的常驻实例，但这与"裸卡"形态矛盾）。
